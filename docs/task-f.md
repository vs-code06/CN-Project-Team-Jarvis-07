# Task F — Caching (Cache-Control, ETag, 304)

## Objective

Demonstrate HTTP caching behavior using `Cache-Control` headers and conditional requests with `ETag` / `If-None-Match`.

## Endpoint

```
GET /api/cached
```

## Response Headers

```
Cache-Control: max-age=60
ETag: W/"19-3Xq2iFjXnMbnAKEagMsqMcjEGaE"
X-Backend: A
```

- `Cache-Control: max-age=60` — tells the client to cache the response for 60 seconds
- `ETag` — a fingerprint of the response body, auto-generated by Express

## Response Body

```json
{
    "data": "static content"
}
```

## How Caching Works

### First Request

```bash
/usr/bin/curl -sI https://app.team1.test/api/cached
```

Response: **200 OK** with `ETag` and `Cache-Control` headers.

### Conditional Request (with If-None-Match)

```bash
/usr/bin/curl -i \
    -H 'If-None-Match: W/"19-3Xq2iFjXnMbnAKEagMsqMcjEGaE"' \
    https://app.team1.test/api/cached
```

Response: **304 Not Modified** — no response body. The server confirms the cached version is still valid.

## Verification Script

See [`scripts/test-cache.sh`](../scripts/test-cache.sh)

The script:

1. Makes an initial request and shows the 200 response with ETag
2. Captures the ETag value
3. Makes a conditional request with `If-None-Match`
4. Shows the 304 Not Modified response

## Why This Matters

In a real network:

- Caching reduces bandwidth usage between client and server
- `304 Not Modified` avoids retransmitting the same data
- The ETag mechanism works at the HTTP layer, on top of the TLS-encrypted connection
